Урок 15. Жизненный цикл GenAI-приложения

Цель: понять, как довести AI-приложение от прототипа до прода и держать его живым Время: ~50 минут Источник: generative-ai-for-beginners/14, опыт практики

Зачем тебе этот урок

У тебя уже есть три рабочих pet-проекта: API-приложение из урока 6, чат-бот из урока 7, semantic search из урока 8, плюс function calling и RAG из 13 и 14. Они работают на твоей машине. Но работающее на твоей машине ≠ продакшен.

Главная разница между «скриптом» и «приложением»: у приложения есть жизненный цикл. Его нужно выпускать, тестировать, мониторить, улучшать. AI-приложения здесь особенно требовательны, потому что:

  • LLM недетерминированы — один и тот же промпт может давать разные ответы.
  • Модели дрейфуют — OpenAI или Anthropic обновили модель, и твой промпт сломался.
  • Цена может взорваться — пользователь повторил один промпт 10 000 раз.
  • Качество трудно измерить — «хорошо ли модель ответила?» субъективно.

Этот урок — карта того, как этим управлять.

1. Шесть этапов жизненного цикла

Любое серьёзное AI-приложение проходит через шесть этапов:

  1. Use case definition — что мы делаем и для кого
  2. Prototyping — первая работающая версия
  3. Evaluation — собираем тесты, измеряем качество
  4. Deployment — выкатываем в прод
  5. Monitoring — следим за метриками и инцидентами
  6. Improvement — итерируем по фидбеку

В отличие от классического software цикла, эти этапы цикличны — после Improvement идём снова на Evaluation. И почти всегда крутятся параллельно: один фичу мониторим, другую прототипируем.

2. Этап 1: Use case — без него всё бесполезно

Самая частая ошибка: «давайте сделаем AI-чат-бот для нашего сайта». Это не use case, это технология. Правильный use case отвечает на три вопроса:

  • Какую задачу пользователя мы решаем? (не «бот», а «помочь клиенту быстро найти подходящий тариф»)
  • Как сейчас решается без AI? (живой менеджер, FAQ, поиск)
  • Почему AI лучше / быстрее / дешевле / приятнее?

Если на третий вопрос нет ответа — не делай AI. Используй существующее. «AI ради AI» — провал.

3. Этап 2: Prototyping — быстро, грязно, работающе

Цель прототипа: проверить гипотезу за неделю или меньше. Не идеальный код, не масштабируемая архитектура — рабочий MVP.

Что важно на этом этапе:

  • Используй самую сильную модель (GPT-4o, Claude Sonnet) — потом оптимизируем
  • Пиши гибкий промпт, не вылизывай
  • Тестируй на 10–20 реальных кейсах, не на 1000
  • Не строй сложную инфру — пусть это будет Python-скрипт или Streamlit

Сильный совет: покажи прототип реальным пользователям как можно раньше. На этом этапе ты узнаешь, что половина того, что казалось важным, не нужно — а нужно что-то совсем другое.

4. Этап 3: Evaluation — главная отличительная черта AI-разработки

У обычного приложения есть unit-тесты: «функция вернула X для входа Y». У AI-приложения такого нет — на одинаковый запрос модель может ответить разными словами, и оба ответа могут быть правильными.

Поэтому используется eval-фреймворк: набор тестовых случаев + способ оценить ответ.

Тест-сет (golden dataset)

Набор кейсов, на которых ты проверяешь приложение:

{
  "id": "tc_001",
  "input": "Можно ли сменить тариф в середине месяца?",
  "expected_topics": ["возможность смены", "перерасчёт", "сроки"],
  "expected_tone": "дружелюбный, конкретный",
  "must_include_link": "/help/change-plan"
}

20–50 кейсов хватает на старте. Со временем расширяй до 200–500.

Как оценивать ответ

Четыре подхода:

  1. Точные совпадения — для structured output (JSON-схема правильная? всё на месте?)
  2. Регулярки / правила — содержит ли ответ нужную ссылку, не содержит ли запрещённых слов
  3. LLM-as-judge — вторая модель (GPT-4) оценивает ответ первой по критериям
  4. Human review — самое дорогое, но иногда необходимое

На практике используется комбо: автоматические проверки (1, 2, 3) на каждом коммите + human review раз в неделю.

Инструменты для eval

  • Promptfoo — CLI и YAML конфиги, регрессионные тесты для промптов. Самый практичный для старта.
  • Inspect — от UK AI Safety Institute, упор на безопасность.
  • Langfuse — observability + eval в одном.
  • Свой скрипт — 100 строк Python с pytest. Часто этого хватает.

5. Этап 4: Deployment — куда выкатить

Базовые варианты в порядке возрастания сложности:

СпособКогда подходитМинусы
Streamlit CloudВнутренние инструменты, демо для друзейНе для большой нагрузки
Vercel / NetlifyFrontend + serverless backendЛимиты длинных запросов (10 сек)
Railway / Render / Fly.ioLong-running апи, простой деплой$5–20/мес
AWS / GCP / AzureСерьёзный масштабСложно, дорого, много возможностей напортачить

Главные технические заботы при деплое AI-приложения:

  • Секреты: API ключи в env vars, не в коде
  • Rate limits: на пользователя и на endpoint
  • Таймауты: LLM-вызов может занять 30+ секунд, обычные web-фреймворки этого не любят
  • Стриминг: ответ возвращается по частям, нужно настроить SSE
  • Cost limits: hard cap на день/месяц, чтобы не разорить тебя

6. Этап 5: Monitoring — что мерить

Метрики делятся на 4 группы:

Технические

  • Latency: p50, p95, p99 — половина запросов быстрее p50, 5% медленнее p95
  • Error rate: % запросов с ошибкой
  • Throughput: запросов в секунду
  • Stream interruption rate: сколько ответов прервалось на полпути

Финансовые

  • Cost per request: средняя стоимость одного запроса
  • Cost per user per day: сколько на тебе зарабатывает / стоит каждый пользователь
  • Token usage breakdown: input vs output, по моделям

Качественные (AI-специфичные)

  • Hallucination rate: % ответов с фактическими ошибками (через автоматические или ручные проверки)
  • Refusal rate: % отказов модели отвечать
  • User feedback score: thumbs up/down
  • Retry rate: сколько пользователей переспрашивают

Продуктовые

  • Активность: DAU, WAU, retention
  • Engagement: сколько сообщений в сессии
  • Конверсия: дошли ли до целевого действия

Инструменты

  • Langfuse — best free-tier для AI-observability, open source
  • Helicone — прокси перед OpenAI/Anthropic, логирует всё
  • PostHog — продуктовая аналитика + AI-фичи
  • Sentry — ошибки и performance

7. Этап 6: Improvement — закрываем цикл

После запуска поступает реальный фидбек — логи, оценки, жалобы. Что с этим делать:

  1. Анализ топ-10 проблемных кейсов в неделю. Не пытайся починить всё — найди 10 худших и разберись.
  2. Добавляй их в test-set. Каждая жалоба становится регрессионным тестом.
  3. Итерируй промпт или add knowledge через RAG. Не fine-tune сразу — это последний ресурс.
  4. A/B-тестируй новую версию: 10% пользователей на новой, 90% на старой. Через неделю — смотри метрики.
  5. Rollback план — если новое плохо, моментально вернись.

8. Pitfalls — частые грабли

Slack-driven development

«Менеджер написал в Slack — модель отвечает плохо на X» → разработчик молниеносно правит промпт → завтра новая жалоба про Y → правка → Z → ...

Без eval-сета вы реактивно носитесь за каждой жалобой, ломая то, что работало.

Версии моделей

OpenAI обновляет gpt-4o без предупреждения. Ваш протестированный промпт может начать вести себя иначе. Используйте версии: gpt-4o-2024-11-20 вместо просто gpt-4o.

Стоимость без лимитов

Одного бага достаточно: пользователь зацикливается на «попробуй ещё раз», вы платите $500 за день. Хард-лимиты на пользователя обязательны.

Логирование PII

Если в промптах от пользователей паспортные данные и т.п. — это всё попадает в ваши логи Langfuse / Sentry. Юридический риск. Маскируйте перед логированием.

9. Глоссарий

  • Eval / Evaluation — систематическая оценка качества AI-приложения
  • Golden dataset — эталонный набор тестовых кейсов
  • LLM-as-judge — вторая модель оценивает ответ первой
  • Drift — изменение поведения модели со временем (обновили модель → промпты сломались)
  • Observability — возможность видеть, что происходит внутри приложения в проде
  • A/B testing — две версии параллельно, сравниваем метрики
  • Hallucination rate — % ответов с выдуманными фактами
  • Refusal rate — % отказов модели отвечать (безопасность срабатывает)
  • Cost per request / per user — финансовые KPI
  • Promptfoo — open-source CLI для регрессионных тестов промптов
  • Langfuse — open-source платформа AI-observability и eval

10. Практика (60 минут)

Упражнение 1. Eval-сет для своего проекта (20 минут)

Возьми один из своих pet-проектов (бот из урока 7 или RAG из урока 8).

  1. Запиши 20 реальных запросов, которые ты задавал ему
  2. Для каждого запроса — что было бы идеальным ответом? (1-2 предложения)
  3. Сохрани в tests.jsonl: 
    {"input": "...", "expected_topics": [...], "must_not_say": [...]}

Упражнение 2. Promptfoo (20 минут)

npm install -g promptfoo
promptfoo init

В promptfooconfig.yaml:

prompts:
  - "Ответь на вопрос пользователя: {{question}}"
providers:
  - openai:gpt-4o-mini
  - openai:gpt-4o
tests:
  - vars: { question: "Что такое RAG?" }
    assert:
      - type: contains
        value: "Retrieval"
      - type: llm-rubric
        value: "Ответ объясняет RAG понятным языком"

Запусти promptfoo eval. Сравни две модели на одних кейсах.

Упражнение 3. Cost monitoring (20 минут)

Возьми свой бот из урока 7. Добавь подсчёт usage.total_tokens к каждому вызову. Сохрани в файл usage.jsonl.

Через неделю использования посмотри: сколько токенов потратил, на чём, был ли спайк (день с резко большим расходом). Это базовый cost monitoring своими руками.

11. Проверь себя

1. Чем отличается тестирование AI-приложения от обычного?
LLM недетерминирован — на одинаковый промпт может давать разные ответы. Поэтому используют eval-сеты (наборы кейсов с ожиданиями) и LLM-as-judge вместо unit-тестов.

2. Что такое golden dataset?
Эталонный набор тестовых случаев (20–500 штук), на котором проверяешь приложение после каждого изменения. Защищает от регрессий.

3. Когда использовать LLM-as-judge?
Когда автоматические проверки (регулярки, точные совпадения) не подходят — например, оценить тон, креативность, корректность пересказа. Минус: дорого и сама LLM-судья может ошибаться.

4. Что такое drift модели?
Изменение поведения модели со временем. OpenAI / Anthropic обновляют свои модели, и старые промпты могут вести себя иначе. Фикс: пиннить версии моделей и тестировать перед апгрейдом.

5. Назови 3 финансовых KPI для AI-приложения.
Cost per request, cost per user per day, token usage breakdown (input vs output).

6. Что значит p95 latency?
95% запросов обработаны быстрее этого значения. Если p95 = 3 сек — значит каждый 20-й пользователь ждёт дольше 3 секунд.

7. Почему важны hard cost limits?
Один баг или зацикливание = $500–5000 за день. Хард-лимиты на пользователя и приложение в OpenAI/Anthropic settings спасают от разорения.

8. Что такое slack-driven development?
Антипаттерн: реактивно правишь промпты по каждой жалобе из Slack без eval-сета. Ломает то, что работало.

9. Когда A/B-тестировать?
Перед мажорным изменением промпта или сменой модели. Маленький процент пользователей (5–10%) на новой, остальные на старой. Сравнить метрики через 3–7 дней.

10. Какой инструмент я бы выбрал для observability с нуля?
Langfuse — open source, бесплатный self-hosted или generous free tier, покрывает логирование + eval + analytics в одном.

12. Что должно остаться в голове

  1. Жизненный цикл AI-приложения цикличен: use case → prototype → eval → deploy → monitor → improve → eval...
  2. Eval — главное отличие от обычной разработки. Без него ты «носишь воду» в реакции на жалобы.
  3. Golden dataset важнее красивого кода.
  4. Пиннить версии моделей — модели дрейфуют без предупреждения.
  5. Hard cost limits обязательны — один баг разорит.
  6. Метрики: технические + финансовые + качественные + продуктовые. Все четыре.
  7. Langfuse + Promptfoo — стартовый stack для серьёзного приложения.
📌 Закрепление: следующий шаг — превратить твой pet-проект в «настоящее» приложение. Eval-сет + хотя бы базовый мониторинг + cost limits. После этого имеешь право назвать его «production-ready».
