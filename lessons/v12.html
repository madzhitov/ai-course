Зачем тебе этот урок

Этот урок — часть «Справочника по веб-разработке для не-разработчиков». Это не ката (как v1–v10), а карта территории. Здесь — концепты, которые AI генерирует в твоих проектах и которые тебе важно понимать, чтобы не быть слепым.

6. Базы данных — где живут данные

Реляционные (SQL)

Данные хранятся в таблицах со связями. Как Excel, но мощнее.

Таблица products:

id name price category_id
1 Кроссовки Air 12000 1
2 Рюкзак Urban 5500 2

Таблица categories:

id name slug
1 Обувь shoes
2 Сумки bags

Связь: products.category_id → categories.id. Один запрос — получаешь товар с категорией.

SELECT products.name, products.price, categories.name as category
FROM products
JOIN categories ON products.category_id = categories.id
WHERE categories.slug = 'shoes';

PostgreSQL — золотой стандарт. Надёжный, мощный, бесплатный.

NoSQL (документные)

Данные хранятся как JSON-документы, без жёсткой схемы.

{
  "id": "abc123",
  "name": "Кроссовки Air",
  "price": 12000,
  "category": "Обувь",
  "details": {
    "material": "Кожа",
    "colors": ["black", "white"],
    "sizes": [40, 41, 42, 43]
  }
}

Гибко (можно добавить любое поле без миграции), но сложнее делать связи и аналитику.

MongoDB — самая популярная NoSQL. Firebase Firestore — от Google, удобна для мобильных приложений.

Supabase — бэкенд из коробки

Supabase = PostgreSQL + готовые обёртки. Вместо написания SQL вручную:

// Получить все товары категории «Обувь»
const { data } = await supabase
  .from('products')
  .select('name, price, categories(name)')
  .eq('categories.slug', 'shoes');

Supabase автоматически генерирует REST API для каждой таблицы. Создал таблицу — API готов. Плюс авторизация, хранилище файлов, realtime-подписки — всё в одной коробке.

ORM — прослойка между кодом и базой

ORM (Object-Relational Mapping) позволяет работать с базой как с объектами в коде, без написания SQL.

Prisma (самый популярный для TypeScript):

// Схема (prisma/schema.prisma)
model Product {
  id         Int      @id @default(autoincrement())
  name       String
  price      Int
  category   Category @relation(fields: [categoryId], references: [id])
  categoryId Int
}

// Использование в коде
const products = await prisma.product.findMany({
  where: { category: { slug: 'shoes' } },
  include: { category: true }
});

Drizzle — более лёгкий ORM, ближе к SQL, но с типизацией.

Для вайб-кодинга Supabase SDK достаточно — он проще ORM и отлично работает с AI-генерацией.

Миграции

Миграция — это версионное изменение структуры базы данных. Как Git, но для схемы данных.

-- Миграция: добавляем поле discount в таблицу products
ALTER TABLE products ADD COLUMN discount INTEGER DEFAULT 0;

Миграции позволяют: откатить изменения, синхронизировать базу между разработчиками, деплоить изменения схемы вместе с кодом.

🏋️ Практика

  1. Зарегистрируйся на app.supabase.com (бесплатно)
  2. Создай новый проект
  3. Зайди в Table Editor, создай таблицу products с полями: id, name (text), price (int4)
  4. Добавь 3-5 товаров вручную через интерфейс
  5. Перейди в SQL Editor и выполни: SELECT * FROM products WHERE price > 5000
  6. Ты только что сделал запрос к реальной базе данных

7. API — как части системы общаются

API (Application Programming Interface) — это контракт между двумя системами: «если ты пришлёшь мне запрос в таком формате, я отвечу в таком формате».

REST API

Самый распространённый тип. Использует HTTP-методы:

  • GET — получить данные. GET /api/products → список товаров
  • POST — создать. POST /api/orders + тело запроса → новый заказ
  • PUT/PATCH — обновить. PATCH /api/products/1 → изменить товар
  • DELETE — удалить. DELETE /api/products/1 → удалить товар

Ответ приходит в формате JSON:

{
  "data": [
    { "id": 1, "name": "Кроссовки Air", "price": 12000 },
    { "id": 2, "name": "Рюкзак Urban", "price": 5500 }
  ],
  "total": 2
}

Webhook

Webhook — это «обратный API». Вместо того чтобы ты спрашивал сервер «есть новый заказ?» каждую секунду, сервер сам стучится к тебе, когда заказ появляется.

Примеры: - Telegram Bot — Telegram присылает webhook на твой сервер при каждом сообщении боту - Stripe / ЮKassa — присылают webhook при успешной оплате - GitHub — присылает webhook при каждом push в репозиторий

Статус-коды HTTP

  • 200 — Ок, всё хорошо
  • 201 — Создано (после POST)
  • 301 — Перенаправление (постоянное)
  • 400 — Плохой запрос (ошибка клиента)
  • 401 — Не авторизован (нет токена)
  • 403 — Запрещено (токен есть, но прав нет)
  • 404 — Не найдено
  • 500 — Ошибка сервера

🏋️ Практика

  1. Открой терминал и выполни: curl https://jsonplaceholder.typicode.com/posts/1
  2. Ты только что сделал GET-запрос к API и получил JSON-ответ
  3. Попробуй: curl https://jsonplaceholder.typicode.com/posts?userId=1 — фильтрация через query params
  4. Открой DevTools → Network на любом сайте и посмотри статус-коды запросов

8. Авторизация — кто ты и что тебе можно

Аутентификация vs Авторизация

Аутентификация — кто ты? Процесс подтверждения личности. Логин + пароль, отпечаток пальца, Face ID.

Авторизация — что тебе можно? Проверка прав. Обычный пользователь видит свои заказы, админ видит все заказы.

Как работает сессия

  1. Пользователь вводит email + пароль
  2. Сервер проверяет: хэширует пароль и сравнивает с хэшем в базе
  3. Если совпало — генерирует JWT-токен (JSON Web Token)
  4. Токен отправляется браузеру и сохраняется в cookie
  5. При каждом следующем запросе браузер автоматически отправляет cookie с токеном
  6. Сервер проверяет токен и понимает, кто делает запрос

JWT-токен

JWT — это зашифрованная строка из трёх частей:

eyJhbGciOiJIUzI1NiJ9.eyJ1c2VyX2lkIjoxMjN9.SflKxwRJSMeKKF2QT4fwpMeJf36POk6yJV_adQssw5c

Внутри (если расшифровать среднюю часть):

{
  "user_id": 123,
  "email": "user@example.com",
  "role": "admin",
  "exp": 1717200000
}

Токен подписан секретным ключом сервера. Если кто-то изменит содержимое — подпись не совпадёт, сервер отклонит.

OAuth — «Войти через Google»

Вместо хранения паролей ты делегируешь аутентификацию Google/Yandex/VK:

  1. Пользователь нажимает «Войти через Google»
  2. Перенаправляется на Google, вводит свой пароль Google
  3. Google спрашивает: «Разрешить сайту X доступ к вашему email?»
  4. Пользователь соглашается
  5. Google отправляет код на твой сервер
  6. Твой сервер обменивает код на данные пользователя (email, имя)
  7. Создаётся сессия — без хранения чужого пароля на твоей стороне

RLS (Row Level Security)

Защита на уровне базы данных в Supabase/PostgreSQL. Пишешь правила прямо в базе:

-- Пользователь видит только свои заказы
CREATE POLICY "Users see own orders"
  ON orders FOR SELECT
  USING (auth.uid() = user_id);

-- Админ видит все заказы
CREATE POLICY "Admins see all orders"
  ON orders FOR SELECT
  USING (auth.jwt() ->> 'role' = 'admin');

Даже если в коде баг — база не отдаст чужие данные. Второй рубеж обороны.

Готовые решения (не пиши авторизацию с нуля)

  • Supabase Auth — встроено в Supabase, поддерживает email, OAuth, magic links
  • Clerk — красивые готовые компоненты для входа/регистрации
  • NextAuth (Auth.js) — библиотека для Next.js, гибкая
  • Firebase Auth — от Google, простая интеграция

🏋️ Практика

  1. В своём проекте Supabase зайди в Authentication → Settings
  2. Включи Email provider (включён по умолчанию)
  3. Попробуй создать пользователя через Authentication → Users → Add User
  4. Зайди на jwt.io, вставь любой JWT-токен — увидишь его содержимое в расшифрованном виде
