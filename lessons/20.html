Урок 20. Agentic RAG

Цель: понять, как RAG превращается в агентский паттерн, и когда это нужно Время: ~55 минут Источник: ai-agents-for-beginners/05

Зачем тебе этот урок

Классический RAG (Урок 14) = «один поиск, один ответ». Это решает 70% запросов. Но когда вопрос сложнее одного факта — классический RAG ломается.

«Сравни нашу политику возврата с конкурентом X за последние 2 года». Это:

  • Несколько поисковых запросов.
  • В разных источниках.
  • С последующим объединением.

Agentic RAG — это когда модель сама решает, что искать, в каком источнике, и когда остановиться. К концу урока ты будешь понимать, чем это отличается, и когда оправдано.

1. Чем отличается от классического RAG

Классический RAGAgentic RAG
Поисковых запросов11–N (модель решает)
Источников1 (обычно vector DB)Несколько (vector + SQL + web + API)
Решение «что искать»Прямо запрос пользователяМодель переформулирует / разбивает
Решение «достаточно ли»—Модель сама останавливается
Стоимость на запрос$0.01–0.05$0.05–0.50
Латентность1–3 сек5–30 сек

2. Когда обычный RAG не справится

  • Multi-hop вопросы. «Кто CEO компании, которая купила Figma в 2022?» — два связанных факта.
  • Сравнения. «Чем наша цена отличается от рыночной».
  • Агрегация. «Сколько у нас контрактов с штрафом больше $10k».
  • Условные запросы. «Если есть упоминание X — найди связанное Y».
  • Гибридные данные. Документы + БД + актуальные новости.

3. Базовый паттерн Agentic RAG

while not ready:
    plan = llm("Какие подзапросы нужны?")
    for query in plan.queries:
        results = retrieve(query, source=plan.source)
        evidence.append(results)
    if llm("Достаточно ли данных для ответа?"):
        ready = True
return llm("Сформулируй ответ", evidence)

Это while-loop: модель планирует → ищет → проверяет достаточность → продолжает или останавливается.

4. Sub-question decomposition

Перед поиском модель разбивает сложный вопрос на простые.

Вопрос: «Сравни нашу политику возврата с Amazon»

Декомпозиция:

  1. Какая у нас политика возврата?
  2. Какая у Amazon политика возврата?
  3. В чём ключевые отличия?

Каждый подвопрос — один поиск. Дальше модель сводит результаты.

5. Multi-source retrieval

Реальные данные не в одном месте. Agentic RAG может ходить по разным источникам:

  • Vector DB — для документов, заметок.
  • SQL — для структурированных данных (orders, users).
  • Web search — для актуальных фактов.
  • Internal API — статус сервиса, текущие метрики.
  • Graph DB — для связей (кто кому подчиняется).

Каждый источник = отдельный tool. Модель выбирает по описанию (см. Урок 19).

6. Self-RAG: проверка достаточности

После каждого поиска модель спрашивает себя: «Хватит данных для ответа?»

Evidence so far: [результаты 3 поисков]
Original question: [вопрос пользователя]

1. Какие части вопроса покрыты?
2. Какие НЕ покрыты?
3. Если есть пробелы — какие подзапросы нужны?

Если всё покрыто — ответь "DONE". Иначе — JSON с новыми подзапросами.

Это позволяет агенту останавливаться, когда хватит, и продолжать, когда нет.

7. Корректирующий цикл (Corrective RAG)

Что если первый поиск вернул мусор? Классический RAG отдаст мусор в ответ. Agentic — может:

  • Оценить релевантность результатов (через ту же модель).
  • Если плохо — переформулировать запрос и попробовать снова.
  • Если три попытки — все плохие — честно сказать «не нашёл».

8. Пример: Agentic RAG над Confluence + Jira

Запрос: «Какой статус релиза 3.2 и какие там основные риски?»

  1. План: найти страницу про релиз 3.2 в Confluence + найти открытые тикеты с меткой "release-3.2" в Jira.
  2. Tool calls (параллельно):
    • search_confluence("release 3.2 status")
    • search_jira(label="release-3.2", status="open")
  3. Анализ: «нашёл план, но не нашёл рисков напрямую. Ищу тикеты с меткой risk».
  4. Доп. tool call: search_jira(label="risk", linked_to="3.2")
  5. Финал: сводный ответ со ссылками на источники.

9. Когда НЕ использовать Agentic RAG

  • Простые фактологические вопросы. «Какой у нас IBAN?» — обычный RAG быстрее и дешевле в 10 раз.
  • Нет нескольких источников. Если всё в одной vector DB — multi-hop часто избыточен.
  • Жёсткая латентность. Чат-бот с UX requirement «ответ за 2 секунды» — Agentic не уложится.
  • Малый бюджет. 10 цепочек tool calls × $0.05 = $0.50 за запрос. Может быть много.

10. Инструменты для реализации

  • LangGraph — лучший фреймворк для agentic RAG (state machine, retries, чекпоинты).
  • LlamaIndex — встроенные query engines для multi-step.
  • Haystack — pipeline-based, тоже хорошо.
  • С нуля на Anthropic SDK — для понимания, 100–200 строк.

11. Тонкости и подводные камни

  • Бесконечные циклы. Модель «никогда не уверена» → бесконечно ищет. Ставь max_iterations=5–8.
  • Каскадирующие ошибки. Плохой первый поиск → плохое решение «искать дальше». 5 шагов × 80% точности = 33% итоговой.
  • Дороговизна. Каждый шаг = LLM call + retrieve. Логируй стоимость на запрос.
  • Halucination мерджа. При сведении нескольких источников модель может выдумать связи, которых нет. В промпте: «Указывай источник для каждого утверждения».
  • Промптовая инъекция в retrieved data. Если в одном из документов спрятана инструкция «игнорируй предыдущие правила» — модель послушается. Защита: явно отделять данные XML-тегами + ругаться на инструкции внутри них.

12. Глоссарий

Multi-hop reasoning

Связывание нескольких фактов для одного ответа.

Sub-question decomposition

Разбиение сложного вопроса на простые подзапросы.

Self-RAG

Агент сам проверяет достаточность найденных данных и решает, продолжать ли поиск.

Corrective RAG

Цикл: оценить релевантность → если плохо, переформулировать → попробовать снова.

  4. Протестируй на 3 сложных вопросах (compare, aggregate, conditional).
  5. Сравни: точность classical vs agentic, стоимость, латентность.

14. Проверь себя

1. Чем agentic RAG отличается от классического?
Модель сама решает: что искать, где, и когда остановиться. Несколько источников, несколько шагов.

2. Что такое sub-question decomposition?
Разбиение сложного вопроса на простые подзапросы перед поиском.

3. Когда agentic RAG избыточен?
Простые фактологические запросы, один источник, жёсткая латентность, малый бюджет.

4. Что защищает от бесконечного цикла поиска?
max_iterations + self-check «хватит ли данных» + явное правило «если не нашёл за N попыток — скажи не знаю».

5. Чем опасна промпт-инъекция в retrieved data?
Документ может содержать инструкции, которые модель послушно выполнит. Защита: XML-теги + явное игнорирование инструкций внутри данных.

15. Что должно остаться в голове

  1. Agentic RAG = классический RAG + while-loop с decomposition + multi-source + self-check.
  2. Используй когда: multi-hop, сравнения, агрегация, гибридные источники.
  3. НЕ используй для простых фактологических запросов.
  4. Цена и латентность — в 5–10 раз выше классического RAG.
  5. Защищай от: бесконечных циклов, каскадирующих ошибок, prompt injection в данных.
  6. LangGraph — основной фреймворк. Anthropic SDK — для понимания.
📌 Закрепление: agentic RAG — не «всегда лучше», а «когда оправдано». Большинство юзкейсов решаются классическим. Используй мощь только тогда, когда она нужна.
