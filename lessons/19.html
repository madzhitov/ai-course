Урок 19. Использование инструментов агентами

Цель: проектировать tools для агентов так, чтобы они работали стабильно и были безопасны Время: ~60 минут Источник: ai-agents-for-beginners/04 + Anthropic «Tool use best practices»

Зачем тебе этот урок

Function calling (Урок 13) — это «как технически вызвать tool». Этот урок — «как спроектировать tools для агента так, чтобы он реально работал». 80% багов агентов в проде — это не модель, а плохо спроектированные инструменты.

К концу урока ты сможешь:

  • Решать, какие операции выносить в tools, а какие оставлять модели.
  • Писать описания (descriptions) так, чтобы агент выбирал правильно.
  • Делать tools idempotent и safe-by-default.
  • Группировать tools в наборы под задачу.

1. Что такое tool в современном понимании

Tool — это именованная функция с описанием и схемой параметров, которую модель может вызвать в ходе работы.

{
  "name": "get_weather",
  "description": "Получить текущую погоду в городе",
  "input_schema": {
    "type": "object",
    "properties": {
      "city": { "type": "string", "description": "Название города на русском" },
      "units": { "type": "string", "enum": ["celsius", "fahrenheit"] }
    },
    "required": ["city"]
  }
}

Модель видит этот JSON и решает: вызывать ли, с какими параметрами, что делать с результатом. Всё остальное — твоя ответственность.

2. Что выносить в tools, а что нет

Вынести в toolОставить модели
Получение свежих данных (поиск, БД, API)Анализ и интерпретация
Действия с побочным эффектом (отправка письма, запись в БД)Решение «что делать дальше»
Точные расчёты (Python для математики)Объяснение результата
Доступ к приватным данным юзераФорматирование ответа
Любая операция, где галлюцинация = катастрофаТворческие задачи

Антипаттерн: делать tool для «сгенерируй ответ на основе X». Это уже умеет модель сама, не плоди прокси.

3. Description — главное оружие

Модель выбирает tool по его description. Плохое описание = модель не вызовет нужный tool или вызовет не тот.

Плохо:

"description": "Поиск"

Хорошо:

"description": "Полнотекстовый поиск по базе документов компании. Возвращает топ-5 самых релевантных абзацев. Использовать когда пользователь спрашивает фактологический вопрос о продукте, политиках, истории компании. НЕ использовать для текущих новостей или общих знаний о мире."

Что включать:

  • Что делает (одна фраза).
  • Когда использовать (1–2 примера).
  • Когда НЕ использовать — критично, помогает агенту не путать tools.
  • Формат возврата (одна фраза).

4. Параметры — тоже описывай

Description для каждого параметра — не лень, а необходимость:

"city": {
  "type": "string",
  "description": "Город на русском. Например: 'Москва', 'Санкт-Петербург'. Если пользователь дал английское название — переведи."
}

Без описания модель путает: «Питер» → передаёт «Питер» вместо «Санкт-Петербург», API не находит.

5. Идемпотентность и безопасность

Идемпотентный tool — повторный вызов с теми же параметрами даёт тот же результат и не делает ничего лишнего.

  • ✅ get_user(id=123) — идемпотентный (read-only).
  • ❌ send_email(to, body) — НЕ идемпотентный (каждый вызов = новое письмо).

Модели могут повторять вызовы при сбоях или из-за «думают, что не сработало». Поэтому неидемпотентные tools должны:

  1. Принимать idempotency_key или request_id — клиент его генерирует, сервер проверяет, что не выполнял.
  2. Возвращать чёткое подтверждение: «отправлено по ID 12345».
  3. Для критичных действий — требовать confirmation flag: send_email(to, body, confirmed=true). Модель должна явно подтвердить.

6. Принцип least privilege

Tool должен делать ровно одно, а не «всё про пользователей».

Плохо: manage_user(action, user_id, ...) — может удалить, создать, обновить. Опасно.

Хорошо: три отдельных tool:

  • get_user(id) — read-only.
  • update_user_name(id, name) — узкое действие.
  • delete_user(id, confirmed=true) — критичное, с явным флагом.

Узкие tools легче описать, легче ограничить, легче дебажить.

7. Группировка tools в наборы

Если у тебя 50 tools — модель путается. Решение: toolset under intent.

Сначала модель выбирает «какой задачей сейчас занимаемся» (research, send_email, query_db) — это router. Дальше открывается набор из 3–5 tools под эту задачу.

На практике:

  • В системном промпте — «у тебя есть три режима: explore (поиск), act (действия), reflect (анализ)».
  • В каждый момент — даёшь модели только tools одного режима.
  • Когда модель решает «теперь нужно действовать» — она переключает режим.

8. Что возвращать tool'у

Модель читает результат. Если результат — 10MB JSON, она утонет.

Правила хорошего результата:

  • Кратко. 500–2000 символов максимум на ответ. Если данных больше — пагинация или summary.
  • Структурированно. JSON, не сырой HTML.
  • С пометкой об ошибках. {"error": "user not found", "user_id": 123} — модель прочитает и нормально среагирует. Не выкидывай stack trace в return.
  • С метаданными. {"results": [...], "total": 1500, "showing": 5} — модель поймёт, что есть ещё, и спросит уточнение.

9. Streaming и параллельные tool calls

Современные модели (Claude 3.5+, GPT-4o) умеют:

  • Параллельные tool calls — модель за один шаг вызывает 3–5 tools одновременно. Если три запроса независимы — это в 3 раза быстрее.
  • Streaming с tool use — модель может стримить размышление, потом вызвать tool, потом стримить дальше.

Что это значит для тебя: когда проектируешь, думай — какие tools могут идти параллельно? Если да — модель сама их распараллелит, без особых усилий.

10. Тонкости и подводные камни

  • Слишком много tools. Больше 15 в одном наборе — модель начинает выбирать хаотично. Группируй.
  • Совпадающие имена. search() и find() — модель путает. Используй разные глаголы или namespace: db_search vs web_search.
  • Игнор ошибок tool. Модель часто продолжает «как будто всё ок», даже если tool вернул error. Возвращай ошибки явно и предсказуемо.
  • Долгие tools. Если tool работает 30 секунд — пользователь не дождётся. Сделай async: возвращай job_id, потом polling tool для статуса.
  • Нет audit log. В проде — обязательно логируй каждый вызов: какой tool, с какими параметрами, что вернул, сколько занял.

11. MCP — стандарт для tools (упоминание)

В 2024 Anthropic выпустили Model Context Protocol — открытый стандарт описания tools. Любой MCP-сервер можно подключить к Claude, Cursor, Zed, ChatGPT GPTs (через переходники).

Подробнее — Урок 28 «Агентские протоколы (MCP)» и мини-проект p3 «Свой MCP-сервер».

12. Глоссарий

Tool / Function

Именованная функция с описанием и схемой, которую модель может вызвать.

Tool description

Текстовое описание, по которому модель выбирает tool. Главное оружие проектировщика.

Idempotency key

Уникальный ключ запроса. Сервер проверяет, что не выполнял ранее с тем же ключом.

Least privilege

Принцип «минимум прав». Tool делает ровно одно действие.

Parallel tool use

Модель вызывает несколько независимых tools одновременно.

13. Практика (60 минут)

  1. Возьми задачу: «помощник, который ищет в моих Notion-заметках и создаёт там же новые задачи».
  2. Спроектируй 4–5 tools: search_notes, get_note, create_task, update_task_status, list_tasks.
  3. Напиши для каждого description (включая «когда НЕ использовать»).
  4. Реализуй на Anthropic SDK с tool_use.
  5. Протестируй на 5 разных запросах. Где агент промахнулся — улучши description.
  6. Запиши в progress.md — какие правки описаний дали максимальный эффект.

14. Проверь себя

1. Что выносить в tools, что оставлять модели?
В tools — данные, действия, точные расчёты. Модели — анализ, интерпретация, формулировки.

2. Что важнее: схема параметров или description?
Description. Если схема правильная, но описание плохое — модель не вызовет.

3. Что такое идемпотентность и зачем она tools'ам?
Повторный вызов с теми же параметрами = тот же результат. Защита от повторных вызовов модели при сбоях.

4. Чем плох tool manage_user(action, ...)?
Слишком широкий. Лучше отдельные узкие tools — легче ограничить, описать и дебажить.

5. Когда нужна группировка tools?
Когда их больше 15. Группируй по intent/режиму: «explore», «act», «reflect».

15. Что должно остаться в голове

  1. В tools — данные и действия. Модели — интерпретация.
  2. Description с «когда использовать» И «когда НЕ использовать» — критично.
  3. Идемпотентность для критичных действий. Idempotency key.
  4. Least privilege: узкие tools, не швейцарские ножи.
  5. Группируй tools по intent если их больше 15.
  6. Возвращай кратко, структурированно, с метаданными.
  7. Параллельные tool calls — бесплатное ускорение.
  8. Audit log в проде — обязательно.
