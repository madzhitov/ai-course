Prompt Caching — экономим 90% на длинных контекстах

Цель: освоить prompt caching Anthropic для серьёзной экономии денег Время: ~35 минут Источник: docs.claude.com/build-with-claude/prompt-caching

Зачем тебе этот урок

У тебя приложение, где в каждом запросе один и тот же system prompt на 5000 токенов с инструкциями? Каждый вызов ты платишь за эти 5000 токенов заново. На сотне вызовов в день — это уже заметные деньги. На тысячах — критично.

Prompt caching — фича Anthropic, которая позволяет закэшировать стабильную часть промпта и при следующих вызовах платить за неё в 10 раз меньше. Это самая недооценённая оптимизация в работе с LLM.

1. Как работает

Без кэширования (обычный поток):

Запрос 1: [system prompt 5000т] + [user "вопрос 1" 50т]
  → input: 5050 × $3/M = $0.0152

Запрос 2: [system prompt 5000т] + [user "вопрос 2" 50т]
  → input: 5050 × $3/M = $0.0152
  (платим за system prompt снова и снова)

С кэшированием:

Запрос 1: [system prompt CACHED 5000т] + [user 50т]
  → cache write: 5000 × $3.75/M = $0.01875 (+25%)
  → input: 50 × $3/M = $0.00015
  = $0.019 (чуть дороже)

Запрос 2: [system prompt CACHED 5000т] + [user 50т]
  → cache read: 5000 × $0.30/M = $0.0015 (10% от обычной цены!)
  → input: 50 × $3/M = $0.00015
  = $0.00165 (в 9 раз дешевле)

Чем больше повторов — тем больше экономия. После 10 запросов экономия ~85%. После 100 — ~89%.

2. Когда выгодно использовать

Выгодно

  • Длинный system prompt с инструкциями — повторяется в каждом запросе
  • Большой контекст документов (например, в RAG над одной книгой) — много вопросов к одной книге
  • Few-shot примеры — много, на каждый запрос подмешиваются
  • Длинный диалог — закэшировать всю историю до текущего хода

Невыгодно

  • Очень короткие промпты — кэш не покрывает overhead
  • Каждый запрос с новыми данными — нечего кэшировать
  • Один запрос — не повторишь, не сэкономишь

Минимальный размер для кэширования: 1024 токена (для Sonnet/Opus) или 2048 (для Haiku).

3. Цены: запись vs чтение

ОперацияSonnet 4.5Opus 4Haiku
Обычный input$3.00/M$15.00/M$0.80/M
Cache write (+25%)$3.75/M$18.75/M$1.00/M
Cache read (-90%)$0.30/M$1.50/M$0.08/M

Cache write чуть дороже обычного input (+25%). Cache read — в 10 раз дешевле. Поэтому кэш окупается уже на 2-м запросе.

Цены в таблице — ориентир. Anthropic периодически их пересматривает, а названия моделей обновляются. Актуальный прайс всегда здесь: anthropic.com/pricing. Важна не конкретная цифра, а соотношение: write ≈ +25%, read ≈ −90%.

4. Время жизни кэша

Два режима:

  • 5 минут (по умолчанию) — без доплаты
  • 1 час (extended cache, beta) — двойная цена за cache write, но всё ещё дешевле обычной

5 минут — для интерактивных сессий (чат, диалог). 1 час — для batch-обработки, когда несколько запросов с большой паузой.

Кэш можно «дёргать» — каждый раз когда читаешь из него, таймер обнуляется на новые 5 минут (или 1 час).

5. Как использовать в API

Простой пример с Python SDK:

from anthropic import Anthropic

client = Anthropic()

system_prompt = "..." * 5000  # длинный, стабильный

response = client.messages.create(
    model="claude-sonnet-4-5",
    max_tokens=1024,
    system=[
        {
            "type": "text",
            "text": system_prompt,
            "cache_control": {"type": "ephemeral"}  # ← вот так
        }
    ],
    messages=[
        {"role": "user", "content": "Вопрос пользователя"}
    ]
)

# Проверим использование кэша
print(response.usage)
# CacheCreationInputTokens: 5000 (на первом запросе)
# CacheReadInputTokens: 0
# InputTokens: 8 (всё остальное)

На втором вызове с тем же system prompt:

print(response.usage)
# CacheCreationInputTokens: 0
# CacheReadInputTokens: 5000  ← из кэша
# InputTokens: 8

6. Multi-level caching

Можно кэшировать сразу несколько частей промпта. Anthropic поддерживает до 4 cache breakpoint'ов в одном запросе.

Пример с тремя уровнями:

messages.create(
    system=[
        {"type": "text", "text": "Базовые инструкции",
         "cache_control": {"type": "ephemeral"}}     # уровень 1: стабильный
    ],
    messages=[
        {"role": "user", "content": [
            {"type": "text", "text": "Большой документ X...",
             "cache_control": {"type": "ephemeral"}}  # уровень 2: документ
        ]},
        {"role": "assistant", "content": "..."},
        {"role": "user", "content": [
            {"type": "text", "text": "История разговора...",
             "cache_control": {"type": "ephemeral"}}  # уровень 3: история
        ]},
        {"role": "user", "content": "Новый вопрос пользователя"}  # без кэша
    ]
)

Каждый уровень кэшируется независимо. Если документ изменился, кэш на нём сбросится, но базовые инструкции — нет.

7. Реальные кейсы экономии

Чат-бот поддержки

System prompt 3000 токенов + few-shot 4000 токенов. Каждый ответ ~500 токенов output.

  • Без кэша: 7500 × $3 + 500 × $15 = $0.030 за ответ
  • С кэшем (после первого): 7500 × $0.30 + 500 × $15 = $0.010 за ответ
  • Экономия: ~67% на input части

RAG-бот над книгой

Книга 80 000 токенов. Юзер задаёт 10 вопросов в сессии.

  • Без кэша: 10 × 80 000 × $3 = $2.40 за сессию
  • С кэшем: $0.30 (cache write) + 9 × 80 000 × $0.30 = $0.52 за сессию
  • Экономия: 78%

Code agent

Контекст 50 000 токенов кода. 20 итераций агента в задаче.

  • Без кэша: 20 × 50 000 × $3 = $3.00 на задачу
  • С кэшем: 1 × $0.19 + 19 × $0.015 = $0.47
  • Экономия: 84%

8. Подводные камни

Cache не сработает если

  • Минимальный размер не достигнут (1024 токена для Sonnet)
  • Кэш истёк (более 5 минут / 1 часа простоя)
  • В кэшируемой части хоть один символ изменился
  • Модель сменилась — у каждой модели свой кэш

Цена кэширования

Cache write дороже обычного на 25%. Если ты делаешь только 1 запрос — не экономишь. Окупается со 2-го.

Безопасность контекста

Каждый клиент API имеет свой кэш — между разными аккаунтами он не пересекается. Но внутри своего проекта будь осторожен: если в кэше есть пользовательские данные клиента А, другой клиент Б к ним доступа не получит, но в логах твоего бэкенда они есть.

Не путать с PromptShield

В разных провайдерах разные системы. У OpenAI есть свой prompt caching (с 2024), но цена и поведение отличаются. Урок про Anthropic — для OpenAI смотри их доки.

9. Глоссарий

  • Prompt caching — кэширование стабильной части промпта
  • Cache write — первый запрос, формирующий кэш (+25% к цене)
  • Cache read — последующие запросы, читающие из кэша (-90%)
  • Cache breakpoint — место в промпте, где заканчивается кэшируемая часть
  • Ephemeral cache — стандартный 5-минутный кэш
  • Extended cache — 1-часовой кэш (beta, дороже)
  • cache_control — параметр в API для указания кэша

10. Практика (35 минут)

Упражнение 1. Измерь свои расходы (10 минут)

Возьми свой pet-проект (бота из урока 7 или RAG из 14). Прогоняй 10 запросов и логируй usage. Посчитай:

  • Сколько токенов в system prompt?
  • Какую часть запроса можно было бы кэшировать?
  • Сколько бы сэкономил с кэшем?

Упражнение 2. Включи кэш (15 минут)

В своём боте добавь cache_control к system prompt:

system=[{
    "type": "text",
    "text": SYSTEM_PROMPT,
    "cache_control": {"type": "ephemeral"}
}]

Прогоняй сессию из 5–10 запросов. Логируй response.usage.cache_creation_input_tokens и cache_read_input_tokens. Убедись, что после первого запроса всё идёт из кэша.

Упражнение 3. Multi-level (10 минут)

В RAG-боте сделай два уровня кэша: system prompt + большой документ. Проверь usage — должны видеть два уровня кэширования.

11. Проверь себя

1. Цена cache read?
В 10 раз дешевле обычного input (например, $0.30/M для Sonnet вместо $3.00/M).

2. Цена cache write?
На 25% дороже обычного input ($3.75/M для Sonnet). Окупается со второго запроса.

3. Минимальный размер для кэширования?
1024 токена для Sonnet/Opus, 2048 для Haiku.

4. Время жизни стандартного кэша?
5 минут с последнего обращения. Можно расширить до 1 часа в beta.

5. Что кэшировать?
Стабильные части: system prompt, few-shot примеры, большие документы в контексте, историю диалога до текущего хода.

6. Что не кэшируется?
Если в кэшируемой части изменился хотя бы один символ — кэш сбрасывается. Будь аккуратен с динамическими частями.

7. Сколько cache breakpoint'ов поддерживается?
До 4 в одном запросе. Можно кэшировать несколько уровней независимо.

8. Как узнать, что кэш сработал?
В response.usage поля cache_creation_input_tokens (первый раз) и cache_read_input_tokens (последующие).

9. Окупается ли кэш для 1-разовой задачи?
Нет. Cache write дороже обычного. Минимум 2 запроса с одним кэшем.

10. Когда лучше всего работает кэширование?
Когда стабильная часть промпта большая (тысячи токенов) и запросы идут пачкой в интервале до 5 минут.

12. Что должно остаться в голове

  1. Cache read — в 10 раз дешевле обычного input. Это много.
  2. Окупается со 2-го запроса. Cache write +25%.
  3. Минимум 1024 токена для кэширования.
  4. 5 минут жизни кэша — стандарт. 1 час — beta.
  5. До 4 breakpoint'ов в одном запросе — multi-level caching.
  6. Кэшируй: system prompt, few-shot, большие документы, историю.
  7. Не кэшируй: короткие промпты, одноразовые запросы, динамические части.
💰 Закрепление: для серьёзных AI-приложений с тысячами запросов в день prompt caching — это разница между $500/мес и $80/мес. Включи где можешь. Просто проверь в логах, что кэш реально срабатывает.
