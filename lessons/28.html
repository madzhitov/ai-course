Урок 28. Агентские протоколы (MCP)

Цель: понять, зачем агентской экосистеме открытые протоколы, и разобраться в архитектуре MCP и A2A Время: ~50 минут Источник: спецификация MCP (modelcontextprotocol.io) + спецификация A2A

Зачем тебе этот урок

В уроке 13 ты разобрался с function calling, в уроке 19 — с готовыми tools, в уроке 23 — с мульти-агентными системами. Всё это просто, пока не начинаешь строить в масштабе: каждое приложение, дающее модели доступ к внешнему миру, писало свою интеграцию под каждый источник данных.

Агентские протоколы решают именно это. Урок не о том, как заставить модель вызвать инструмент — этому была посвящена практика курса. Урок о стандартах, которые позволяют любому агенту говорить с любым инструментом и агентом на одном языке, независимо от вендора.

1. Проблема M×N

Представь три AI-приложения — чат-бот поддержки, редактор кода, аналитический дашборд — и пять внешних систем: файлы, база данных, Git, таск-трекер, браузер. Без общего протокола каждое приложение пишет свою интеграцию с каждой системой — 15 кусков кода. Добавил систему — плюс три. Добавил приложение — плюс пять. Рост квадратичный: M×N.

Протокол меняет формулу: инструмент один раз описывает себя по стандарту — и с ним работает любое понимающее протокол приложение, а приложение один раз реализует протокол — и получает доступ к любому такому инструменту. Рост линейный: M + N — так же, как когда-то с HTTP, USB, SQL.

2. MCP: Model Context Protocol

MCP — открытый протокол Anthropic, представленный в конце 2024 года: стандартный способ, которым модель получает контекст и вызывает действия во внешних системах. С тех пор он стал индустриальным стандартом — его поддержали OpenAI, Google, Microsoft. Конкурирующие компании, согласившиеся на общий стандарт вместо своего, — сигнал, что проблема была настоящей.

Архитектура строится на трёх ролях: host — приложение пользователя и модели; client — часть host'а для соединения с одним сервером; server — программа, дающая доступ к файлам, базе, API, браузеру.

Сервер описывает себя через три примитива: tools — действия (как в уроках 13 и 19, только описание отдаёт сервер), resources — данные для чтения, prompts — готовые шаблоны запросов. Транспорт двух видов: stdio — для локальных серверов, процесс на этой машине; HTTP — для удалённых серверов в сети.

3. Жизненный цикл соединения и экосистема серверов

Подключение проходит три шага: initialize — рукопожатие о версии и возможностях; discovery — клиент запрашивает у сервера список tools, resources и prompts со схемами (в уроке 13 ты вручную передавал модели JSON-схему функции — здесь схему формирует сам сервер); вызовы — клиент передаёт вызов серверу и возвращает результат. Под капотом это JSON-RPC, формат JSON-сообщений; важно, что это открытый стандарт, а не протокол одной компании.

Вокруг протокола выросла экосистема готовых серверов: файлы, базы данных, браузер, тикеты, поиск. Эффект тот же, что в M×N: кто написал сервер один раз, даёт доступ любому host'у с MCP. Перед интеграцией с нуля проверь, нет ли уже готового сервера.

4. A2A: Agent2Agent

MCP решает задачу «агент ↔ инструменты и данные». Но если агенту нужна помощь не простого инструмента, а полноценного агента, который сам решает задачу? Для этого в 2025 году Google представила A2A — Agent2Agent, переданный в Linux Foundation, под независимую некоммерческую организацию — обычный путь для протоколов-кандидатов в стандарт.

В A2A агенты — равные стороны. Ключевые понятия: agent card — визитка агента с описанием возможностей, по которой понятно, стоит ли поручать ему задачу; tasks — единица работы одного агента для другого, с промежуточными статусами; обмен сообщениями и артефактами — агенты ведут диалог и передают друг другу результаты: текст, файл, данные.

5. MCP vs A2A: вертикаль против горизонтали

MCP — вертикальный протокол: связь агента с тем, что ниже него — инструментами и данными, которые выполняют команду. A2A — горизонтальный: связь с другим агентом того же уровня, который сам мыслит и принимает решения. Протоколы дополняют друг друга: агент может использовать MCP, чтобы дотянуться до базы данных, и A2A, чтобы делегировать часть задачи специализированному агенту — та же логика мульти-агентных систем из урока 23, только связь открыта, а не зашита во внутренний фреймворк.

6. Безопасность протоколов

Открытость протокола — источник рисков. Как только агент может подключиться к любому MCP-серверу, встаёт вопрос доверия.

Доверие серверу. Сервер видит все вызовы и данные, которые через него проходят — это supply chain: недобросовестный сервер может логировать данные или подменять результаты. Подключай только серверы, которым доверяешь.

Tool poisoning. Описание инструмента, которое сервер отдаёт на этапе discovery, может содержать скрытую инъекцию инструкций. Модель читает описание как часть контекста и может среагировать на встроенную команду, даже если пользователь ничего такого не просил.

Скоупы и разрешения. Ограничивай, что может сервер: чтение вместо записи, одна папка вместо всей файловой системы, отдельные учётные данные на каждый сервер. Это продолжение урока 21: там безопасность агентов в целом, здесь новая поверхность атаки; подтверждение опасных действий остаётся за человеком.

7. Мини-пример: скелет MCP-сервера

Скелет сервера на Python в стиле библиотеки fastmcp с одним инструментом. Это иллюстрация архитектуры, а не код для продакшена — сверься с актуальной документацией.

from fastmcp import FastMCP

mcp = FastMCP("weather-server")

@mcp.tool()
def get_weather(city: str) -> str:
    """Возвращает текущую погоду в указанном городе."""
    data = fetch_weather_from_api(city)
    return f"В городе {city} сейчас {data['temp']}°C, {data['condition']}"

@mcp.resource("weather://cities/supported")
def supported_cities() -> str:
    """Список городов, которые поддерживает сервер."""
    return ", ".join(SUPPORTED_CITIES)

if __name__ == "__main__":
    mcp.run(transport="stdio")

Декоратор помечает функцию как tool, docstring становится описанием для discovery, типы параметров — схемой. Рукопожатие, обработку вызовов и формат сообщений берёт на себя библиотека.

9. Глоссарий

MCP (Model Context Protocol)

Открытый протокол связи AI-приложения с внешними инструментами и данными. Сводит M×N интеграций к M+N.

Host / Client / Server

Роли архитектуры MCP: host — приложение пользователя, client — часть host'а для связи с одним сервером, server — программа с tools, resources и prompts.

Discovery

Этап MCP-соединения, на котором клиент запрашивает у сервера список доступных инструментов, данных и шаблонов с описаниями.

A2A (Agent2Agent)

Открытый протокол горизонтальной связи равноправных агентов: agent card описывает возможности, tasks — единицы делегируемой работы.

Agent card

Описание возможностей агента в протоколе A2A — визитка, по которой другой агент решает, стоит ли поручать задачу.

Tool poisoning

Атака, при которой описание инструмента от сервера содержит скрытую инъекцию инструкций, влияющую на поведение модели.

Проверь себя

1. Что решает переход от M×N интеграций к M+N?

«Каждое приложение отдельно интегрируется с каждым инструментом» превращается в «каждая сторона один раз реализует протокол» — рост линейный, а не квадратичный.

2. Какие три примитива предоставляет MCP-сервер?

Tools (действия), resources (данные для чтения), prompts (шаблоны запросов).

3. Из каких шагов состоит жизненный цикл MCP-соединения?

Initialize, discovery (запрос списка tools/resources/prompts), вызовы.

4. Чем A2A отличается от MCP по направлению связи?

MCP вертикален: агент общается с инструментами и данными ниже него. A2A горизонтален: агент общается с равноправным агентом.

5. Что такое tool poisoning?

Внедрение вредоносной инструкции в описание инструмента от сервера — атака через текст, а не через код.

Что должно остаться в голове

  1. Проблема M×N — почему без общего протокола рост интеграций становится неуправляемым.
  2. MCP превращает M×N в M+N: инструмент один раз описал себя по стандарту — работает с любым совместимым клиентом.
  3. MCP открыт Anthropic в конце 2024 года, стал индустриальным стандартом, поддержанным OpenAI, Google, Microsoft.
  4. Архитектура MCP: host — client — server, примитивы tools, resources, prompts.
  5. Транспорт stdio — для локальных серверов, HTTP — для удалённых.
  6. Жизненный цикл: initialize → discovery → вызовы, поверх JSON-RPC.
  7. A2A (Google, 2025, передан в Linux Foundation) — протокол равноправной связи агентов: agent card, tasks, обмен артефактами.
  8. MCP — вертикаль (агент ↔ инструменты/данные), A2A — горизонталь (агент ↔ агент); дополняют друг друга.
  9. Риски протоколов: доверие серверу, tool poisoning, необходимость скоупов и подтверждения человеком.
  10. Выбор: свои функции — function calling; внешние сервисы — MCP; делегирование независимым агентам — A2A.
