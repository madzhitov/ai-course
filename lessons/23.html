Урок 23. Мульти-агентные системы

Цель: научиться проектировать системы из нескольких агентов и выбирать правильную топологию их взаимодействия Время: ~70 минут Источник: ai-agents-for-beginners/08 + доки AutoGen, CrewAI, LangGraph

Зачем тебе этот урок

Один агент с хорошим планировщиком (Урок 22) тянет много задач. Но не все. Когда задача требует разных ролей, разных прав доступа или слишком длинного контекста — один агент начинает захлёбываться. Тогда задачу разбивают между несколькими агентами, каждый из которых хорош в своём.

  • Агент-исследователь и агент-писатель путаются в ролях, если это один промпт на двоих.
  • Контекст одного агента распухает: инструкции для code review смешиваются с инструкциями для маркетинга.
  • Нужно разное «кто может что»: один агент читает базу, другой пишет в прод — и это не должен быть один и тот же процесс.
  • Непонятно, как отлаживать: агент делает 40 шагов подряд, и найти где он свернул не туда — тяжело.

Мульти-агентность решает первые три боли и создаёт четвёртую в квадрате. Это компромисс, а не бесплатное улучшение.

1. Когда мульти-агентность НЕ нужна

Главная ошибка новичка — начинать проект с мульти-агентной архитектуры, потому что «звучит солиднее». Это почти всегда хуже одного хорошо спроектированного агента с tools (Урок 19) и явным планом (Урок 22).

Не строй мульти-агентную систему если:

  • Задача укладывается в 10–15 шагов одного агента с ReAct или Plan-and-Execute.
  • Роли внутри задачи не конфликтуют (один и тот же «стиль мышления» годится для всех шагов).
  • Ты ещё не пробовал один агент с хорошими tools и не упёрся в реальный потолок.

Признаки, что реально нужно несколько агентов:

  • Контекст одного агента раздувается до тысяч строк промпта, потому что там инструкции сразу на три разные роли.
  • Разным частям задачи физически нужны разные права доступа (агент A может писать в БД, агент B — только читать).
  • Задача естественно делится на независимые под-задачи, которые можно выполнять параллельно.
  • Нужна ролевая специализация: один агент лучше работает с промптом «ты — дотошный ревьюер», другой — с промптом «ты — креативный автор», и смешивать их в одном системном промпте вредно.

Правило: сначала всегда пробуй один агент. Мульти-агентность — это решение для задач, которые реально этого требуют, а не архитектурный дефолт.

2. Базовые топологии

Топология — это то, кто кому передаёт управление и данные. Их несколько базовых, и почти все реальные системы — комбинация этих штук.

Orchestrator-workers (супервизор)

Один агент-супервизор получает задачу, разбивает её на подзадачи и раздаёт агентам-воркерам. Воркеры не общаются друг с другом — только с супервизором. Супервизор собирает результаты и решает, что делать дальше.

Пользователь → Супервизор
                 ├→ Воркер A (задача 1)
                 ├→ Воркер B (задача 2)
                 └→ Воркер C (задача 3)
Супервизор ← результаты от A, B, C
Супервизор → финальный ответ пользователю

Плюс: контроль в одном месте, легко добавлять новых воркеров. Минус: супервизор — узкое горлышко, если он ошибся в разбиении — всё поехало.

Sequential pipeline (конвейер)

Агенты идут строго друг за другом. Выход агента A становится входом агента B.

Агент A (сбор данных) → Агент B (анализ) → Агент C (написание отчёта)

Плюс: просто, предсказуемо, легко тестировать каждый шаг отдельно. Минус: медленно (нет параллелизма), один сломанный агент валит всю цепочку.

Parallel + агрегация

Несколько агентов работают одновременно над разными аспектами одной задачи, потом отдельный шаг сводит их результаты воедино.

           ┌→ Агент A (проверяет факты)
Задача →   ├→ Агент B (проверяет стиль)  → Агрегатор → финальный текст
           └→ Агент C (проверяет тон)

Плюс: быстро, если под-задачи независимые. Минус: агрегатору нужно уметь разрешать противоречия между результатами воркеров.

Handoff (передача управления)

Агент сам решает, что задача не в его компетенции, и передаёт управление другому агенту целиком — вместе с контекстом разговора.

Пользователь → Агент "продажи"
  (пользователь спрашивает про баг)
Агент "продажи" → handoff → Агент "техподдержка"
Агент "техподдержка" продолжает разговор с той же историей

Плюс: похоже на то, как работают живые команды (перевод звонка нужному человеку). Минус: нужно аккуратно передавать контекст, иначе новый агент «не в курсе» разговора.

3. Group chat паттерн (AutoGen)

В AutoGen несколько агентов сидят в общем чате и по очереди высказываются, как в групповой переписке. Отдельный агент-менеджер (group chat manager) решает, кто говорит следующим — на основе того, что уже написано в чате.

Чат:
[Пользователь]: Напиши код парсера CSV и проверь его на баги.
[Менеджер]: следующий — Coder
[Coder]: вот функция parse_csv()...
[Менеджер]: следующий — Reviewer
[Reviewer]: нашёл баг — не обрабатывается пустая строка
[Менеджер]: следующий — Coder
[Coder]: поправил, вот новая версия...
[Менеджер]: все согласны, завершаем

Это удобно, когда роли естественно «переговариваются» — как в реальной команде: разработчик пишет, ревьюер проверяет, снова разработчик правит. Минус — легко потерять контроль над тем, сколько раундов займёт разговор.

4. Crew-подход (CrewAI)

CrewAI формализует агентов через три поля: роль (role), цель (goal) и предысторию (backstory) — это всё идёт в системный промпт агента и задаёт его «характер».

researcher = Agent(
    role="Senior Research Analyst",
    goal="Найти точные и актуальные данные по теме",
    backstory="Ты работал 10 лет аналитиком в исследовательской компании, ценишь точность больше скорости."
)

writer = Agent(
    role="Content Writer",
    goal="Превратить сухие данные в понятный текст",
    backstory="Ты пишешь для читателей без технического бэкграунда, избегаешь жаргона."
)

Задачи (tasks) назначаются агентам явно, а порядок выполнения задаёт process:

  • sequential — задачи выполняются строго по очереди, как pipeline.
  • hierarchical — появляется агент-менеджер, который сам решает, кому какую задачу отдать и в каком порядке, ближе к orchestrator-workers.

Crew-подход хорош тем, что роль явно описана словами — это снижает шанс, что агент «перепутает» свою специализацию.

5. Графовый подход (LangGraph)

LangGraph описывает мульти-агентную систему как граф: узлы — это агенты (или функции), рёбра — переходы между ними, причём рёбра могут быть условными («если результат X — иди к агенту B, если Y — к агенту C»). Через весь граф протекает общий state — объект с данными, который каждый узел может читать и дополнять.

graph = StateGraph(AgentState)

graph.add_node("researcher", researcher_node)
graph.add_node("writer", writer_node)
graph.add_node("critic", critic_node)

graph.add_edge("researcher", "writer")
graph.add_conditional_edges(
    "critic",
    lambda state: "writer" if state["needs_revision"] else END
)

graph.set_entry_point("researcher")

Это самый явный и контролируемый способ описать топологию — граф буквально рисует диаграмму, которую ты проектировал на бумаге. Хорош, когда логика переходов сложнее, чем «просто по очереди» или «просто менеджер решает».

6. Общение агентов = токены = деньги

Каждое сообщение между агентами — это токены, за которые ты платишь. В мульти-агентной системе токены считаются не один раз, а на каждом «хопе» между агентами.

  • Каждый агент часто получает всю историю разговора заново — значит с ростом числа реплик стоимость растёт нелинейно.
  • Group chat с 5 агентами и 10 раундами обсуждения может стоить в разы дороже, чем один агент, решивший ту же задачу за 3 tool call'а.
  • Handoff дешевле group chat, если передавать только нужный контекст, а не весь чат целиком.

Как прикидывать стоимость: (число агентов) × (среднее число сообщений на агента) × (средний размер контекста в токенах) × (цена за токен у модели). Если цифра пугает — это сигнал упростить топологию или сократить контекст, который агенты передают друг другу.

Практическое правило: прежде чем строить group chat на 5 агентов, посчитай на бумаге, сколько раундов реально нужно для решения задачи. Обычно оказывается, что 2 агента и pipeline решают ту же задачу в разы дешевле.

7. Отладка мульти-агентных систем

Отладка одного агента — это чтение одной цепочки reasoning. Отладка нескольких агентов — это чтение диалога, где нужно понять, кто, что и кому сказал, и где разговор свернул не туда.

  • Трейсы. Логируй каждое сообщение между агентами с указанием отправителя, получателя и timestamp — без этого невозможно восстановить, что произошло.
  • Кто что сказал. В группе из 4+ агентов легко потерять нить: заведи единый лог с именами агентов, а не просто «assistant: ...».

Типовые фейлы, которые встречаются почти в каждой мульти-агентной системе:

  • Агенты зацикливаются в благодарностях. «Спасибо за уточнение!» → «Рад помочь, обращайтесь если что!» → «Отлично, ещё раз спасибо!» — и так по кругу, пока не кончится лимит раундов. Лечится жёстким системным промптом («не благодари, переходи сразу к делу») и ограничением на число раундов.
  • Супервизор теряет цель. После 5–6 передач управления супервизор забывает исходный запрос пользователя и начинает реагировать только на последнее сообщение воркера. Лечится тем, что исходная цель передаётся в каждом сообщении как отдельное поле, а не полагается на то, что модель «помнит» её из истории.
  • Воркеры дублируют работу. Два воркера, не зная друг о друге, делают одну и ту же под-задачу. Лечится явным разбиением задач в state/плане, а не «пусть агенты сами разберутся».

8. Мини-пример: супервизор + 2 воркера

Упрощённый пример на Python в духе orchestrator-workers — без привязки к конкретному фреймворку, чтобы видна была сама механика:

def supervisor(task):
    # Шаг 1: супервизор разбивает задачу на подзадачи
    subtasks = plan_subtasks(task)  # LLM-вызов, возвращает список

    results = {}
    for subtask in subtasks:
        worker = pick_worker(subtask)  # "researcher" или "writer"
        results[subtask["id"]] = worker(subtask["instruction"])

    # Шаг 2: супервизор собирает результаты в финальный ответ
    return combine_results(task, results)  # ещё один LLM-вызов


def researcher(instruction):
    # ищет факты, возвращает сырые данные
    data = search_tool(instruction)
    return summarize(data)


def writer(instruction):
    # получает данные от researcher через results, пишет текст
    return llm_call(
        system="Ты пишешь понятным языком для нетехнического читателя.",
        user=instruction
    )


def pick_worker(subtask):
    return researcher if subtask["type"] == "research" else writer


# Запуск
task = "Собери 3 факта про рынок EV в 2025 и напиши абзац для блога"
final_answer = supervisor(task)
print(final_answer)

Здесь супервизор делает два LLM-вызова сам (разбиение и сборка), а воркеры вызываются как обычные функции — это уже сама суть orchestrator-workers, а фреймворки типа AutoGen или CrewAI просто оборачивают это в готовые классы и добавляют state-менеджмент, ретраи и логирование.

9. Таблица сравнения топологий

ТопологияКогда использовать
Orchestrator-workersЗадача явно делится на независимые подзадачи, нужен единый контроль
Sequential pipelineШаги строго зависят друг от друга (выход одного = вход другого)
Parallel + агрегацияНесколько независимых проверок/точек зрения на одни и те же данные

10. Глоссарий

Orchestrator-workers

Топология, где один агент-супервизор раздаёт подзадачи агентам-воркерам и собирает их результаты.

Handoff

Передача управления диалогом от одного агента другому вместе с контекстом разговора.

Group chat

Паттерн, где агенты общаются в общем чате по очереди, а менеджер решает, кто говорит следующим.

State (в графовом подходе)

Общий объект с данными, который протекает через все узлы графа и может дополняться каждым агентом.

Backstory

Предыстория агента в CrewAI — текстовое описание характера и опыта, влияющее на стиль его ответов.

Hierarchical process

Режим в CrewAI, где агент-менеджер сам решает порядок и распределение задач между другими агентами.

11. Практика (60 минут)

  1. Возьми задачу: «собрать 3 факта о теме X и написать абзац для блога» (как в мини-примере из раздела 8).
  2. Реализуй её одним агентом с tools (как в Уроке 19) — замерь число tool call'ов и токены.
  3. Реализуй ту же задачу как orchestrator-workers: один супервизор, один воркер-исследователь, один воркер-писатель.
  4. Сравни: время выполнения, суммарные токены, читаемость кода в обоих вариантах.
  5. Добавь к мульти-агентной версии простой лог, который печатает: кто говорит, что получил на входе, что вернул.
  6. Специально сломай одного воркера (пусть возвращает пустой результат) — посмотри, как супервизор на это реагирует, и почини обработку такого случая.
  7. Попробуй посчитать стоимость обеих версий по формуле из раздела 6 (число вызовов × средний размер контекста × цена токена).
  8. Запиши в progress.md: в каком случае мульти-агентная версия оправдала себя, а в каком один агент справился бы не хуже и дешевле.

12. Проверь себя

1. Какая главная ошибка при выборе мульти-агентной архитектуры?
Начинать с неё по умолчанию, не попробовав сначала один агент с хорошими tools и явным планом.

2. Чем orchestrator-workers отличается от sequential pipeline?
В orchestrator-workers супервизор раздаёт независимые подзадачи и собирает результаты; в pipeline агенты идут строго друг за другом, и выход одного — вход следующего.

3. Что решает group chat manager в AutoGen?
Кто из агентов говорит следующим, основываясь на текущем содержимом общего чата.

4. Из чего складывается стоимость мульти-агентной системы в токенах?
Число агентов × среднее число сообщений на агента × средний размер контекста в токенах × цена за токен.

5. Назови два типовых фейла мульти-агентных систем из раздела про отладку.
Агенты зацикливаются в благодарностях; супервизор теряет исходную цель после нескольких передач управления (также подходит: воркеры дублируют работу).

13. Что должно остаться в голове

  1. Сначала всегда пробуй один агент — мульти-агентность нужна не всегда, а начинать с неё по умолчанию — главная ошибка.
  2. Мульти-агентность оправдана при конфликте ролей, разных правах доступа или естественном делении на независимые подзадачи.
  3. Orchestrator-workers — супервизор раздаёт задачи воркерам и собирает результаты.
  4. Sequential pipeline — строгая цепочка, выход одного агента = вход следующего.
  5. Parallel + агрегация — независимые проверки одновременно, потом сведение воедино.
  6. Handoff — передача управления диалогом другому агенту с сохранением контекста.
  7. Group chat (AutoGen) — агенты в общем чате, менеджер решает порядок реплик.
  8. CrewAI формализует роль/цель/backstory агента и порядок задач (sequential/hierarchical).
  9. LangGraph описывает систему как граф с условными переходами и общим state.
  10. Каждое сообщение между агентами — это токены и деньги; считай стоимость до того, как усложнять топологию.
📌 Закрепление: мульти-агентность — это инструмент для конкретной проблемы (конфликт ролей, права доступа, параллелизм), а не архитектура по умолчанию — если один агент справляется, не усложняй.
